# 브라우저 정적 파일 캐시 갱신

## 배경과 변경

사용자는 일반 브라우저에서 입력 문제가 남았으나 캐시를 삭제하고 다시 열자 정상이라고 확인했다. 로그인 성공까지 확인한 보고는 아니다. 앞선 DOM 소유권 실험 후보는 이번 변경에 포함하지 않는다. Browser 패키지는 qa-ime.6 그대로다.

기존 정적 응답에는 Cache-Control이 없고 Starlette의 파일 ETag는 수정 시각과 크기를 사용했다. 다른 내용의 bootstrap이 같은 크기·mtime으로 배포되면 잘못된304로 옛 내용을 재사용할 수 있었다. 고정 URL인 index.html/main.js/dotnet.js와 그 의존 파일을 함께 재검증하도록, 정적 웹 마운트에만 다음 정책을 적용했다.

- Cache-Control:no-cache: 저장 자체는 허용하지만 재사용 전 서버 검증을 요구한다.
- SHA-256 내용 기반 ETag: 동일한 크기·mtime이어도 내용 변경을 구분한다.
- If-None-Match가 일치할 때만304. If-Modified-Since만 있는 구형 요청에는200을 보내 stat 정보만으로 잘못304를 반환하지 않는다.
- 해시는 스레드에서 계산하며 경로/dev/inode/size/mtime_ns/ctime_ns 조합으로 최대512개 캐시한다. 같은mtime/size 덮어쓰기도 ctime 변화로 재계산한다. 별도 파일명 규칙을 추측해 immutable을 지정하지 않는다.

별도 런타임 URL 재작성보다 기존 .NET 게시 구조와 상대 경로를 그대로 유지하는 내용 기반 검증자 정책을 선택했다. API·인증·DB 모델/스키마/개인설정에는 변경이 없다. backend 전체 불변이라는 과거 handoff 설명과 달리 이번 변경은 정적 호스팅 모듈만 바꾼다.

## 검증

- 기존 정적 호스팅/API 우선순위 검사와 신규 캐시 검사를 합쳐28/28 통과.
- GET/HEAD/304에 재검증 정책 유지. 내용이 같으면 ETag304, 내용만 바꾸고mtime/크기를 같게 복원하면200과새본문/새ETag.
- 약한 If-None-Match 및 구형 If-Modified-Since 요청 검사, health/auth API에 캐시 정책을 추가하지 않는 검사 통과.
- 실제 Android 에뮬레이터 Chrome의 동일 프로필·동일 URL에서 캐시 삭제·캐시 비활성화 없이 합성 배포A→B 비교를 실행했다. 실제 계정/DB는 쓰지 않았다. A의 bootstrap을 먼저 로드하고 WASM 다운로드는 지연시킨 후, 같은mtime/size의 B bootstrap으로 교체하고 합성 A WASM을 제거했다.

| 정책 | A 예열 | B 교체 후 같은 URL 탐색 | WASM 요청 |
|---|---|---|---|
| 기존 Starlette 기본 정책 | A bootstrap | A bootstrap 재사용 | 삭제된 runtime.a.wasm,404 |
| 내용 기반 ETag + no-cache | A bootstrap | B bootstrap 수신 | runtime.b.wasm,200 |

이는 최소 정적 모듈 체인의 캐시 전환 검사다. 전체 업무일지 로그인·삼성 실기기의 실사용 검사를 대신하지 않는다. 합성 결과 원문은 browser-cache-transition-results.json이다. 기존 FastAPI on_event/TestClient 사용 중단 예정 경고는 남으며 이번에 불필요한 수명주기 리팩토링을 하지 않았다.

## 한계와 배포 주의

새 헤더는 이미 저장된 옛 응답을 소급해서 무효화하지 못한다. 이미 열려 실행 중인 앱 인스턴스도 자동 교체하지 않는다. 초기 도입 때 구 정책으로 저장된 클라이언트에는 정상 재검증/새 탐색이 필요할 수 있고, 이번 패치가 모든 기존 사용자 캐시를 강제로 갱신한다고 주장하지 않는다. 자동 로그아웃·사이트 데이터 삭제·브라우저 캐시 삭제 코드를 넣지 않았다.

배포 중 파일을 제자리 수정하기보다 검증된 불변 이미지로 교체하는 기존 절차를 유지한다. 이미 실행 중인 구 bootstrap이 아직 받지 않은 옛 자원을 뒤늦게 요청하는 경쟁은 새 헤더만으로 완전히 제거하지 못한다. 롤링 배포에서 옛 fingerprint 자원을 보존하는 정책은 별도 운영 판단이다.

모든 정적 파일이 재검증되므로 캐시된 WASM도304 왕복이 생긴다. 해시 캐시 첫 조회 비용과 일반 재검증 네트워크 비용이 있으며 대규모 성능 측정은 수행하지 않았다. 리버스 프록시가 Cache-Control/ETag를 덮어쓰지 않는지는 NAS 배포 담당이 최종 응답으로 확인해야 한다. 이 커밋 자체는 NAS 배포를 수행하지 않는다.
